# Project Governance Kit v0.2 需求规格：已有项目接入与文档迁移

> 本文是 v0.2 Migration MVP 的中文需求基线。v0.1 只负责新项目初始化；本需求不改变 v0.1 的验收范围。

## 1. 产品目标

为已经存在代码、文档和 Git 历史的项目提供安全、可追踪、可审查的治理接入能力。用户可以选择只补齐治理骨架，或在审查迁移方案后，将已有文档复制为标准治理记录。

Kit 只负责治理文档和迁移记录，不负责重构业务代码，也不把猜测自动变成已确认需求或设计。

## 2. 版本和范围

本需求对应 Kit v0.2 的 Migration MVP。v0.2 的迁移范围限定为 Markdown 和纯文本，其他格式只生成候选映射报告。

### 2.1 补齐模式

补齐模式用于已有项目首次接入 Kit：

- 创建缺失的 `AGENTS.md`、治理目录、模板、索引、状态和活动文件；
- 保留所有已有文件和目录；
- 已有同名文件不覆盖；
- 不移动、重命名、删除或合并已有文档；
- 如果没有 `STATUS.md`，项目阶段为 `adoption_review`；
- 如果已有 `STATUS.md`，不得覆盖或重置其项目阶段；
- 输出已有文件、缺失文件、Git 状态和候选映射。

### 2.2 迁移模式

迁移模式用于把已有文档纳入标准治理目录：

- 先只读扫描，再生成 `MIG-*` 迁移方案；
- 用户可以批量批准方案，也可以逐项排除或保留待审查状态；
- 只复制已经批准的 Markdown 或纯文本文件；
- 原文件保持原路径，不额外保存原文快照；
- 治理副本初始为 `draft`，不能自动成为 `accepted`；
- 治理副本保留来源路径、来源哈希、迁移批次、格式和置信度；
- 无法判断类型、存在敏感内容或格式不支持的文件不得自动复制；
- 迁移结果必须更新 `MIG-*`、相关索引、`ACTIVITY.md`，并产生可验证的 `VER-*` 证据。

## 3. 扫描边界

默认扫描根目录下的治理相关 Markdown/纯文本文件，以及 `docs/`、`doc/`、`documentation/`、`设计/`、`需求/` 等常见文档目录。扫描目录和排除模式可配置。

默认排除 `.git/`、虚拟环境、依赖目录、构建产物、缓存、源代码、测试代码、运行时数据、`.env`、密钥、证书、账号配置和大型二进制文件。

候选项必须包含源路径、建议类型、判断依据、置信度、敏感内容判断和建议动作。文件名或路径只能产生候选建议，不等于内容已经确认。

## 4. 文档和记录模型

新增 `MIG-*` 迁移记录类型，记录一次扫描、批准和执行批次。迁移记录至少包含：

- 扫描范围和排除规则；
- 源文件、目标记录、建议类型和置信度；
- 源文件哈希和生成时间；
- 每个条目的批准、排除、应用、冲突、待审查或失败状态；
- 用户批准依据、执行结果和验证记录；
- branch、HEAD 和工作区状态；
- blocker 和唯一下一步动作。

迁移 ID 使用 `MIG-001` 形式，生成的治理记录使用 `REQ-MIG-001-001`、`DES-MIG-001-002` 等稳定命名，避免与项目已有记录 ID 冲突。

## 5. 副本和冲突规则

- 原文件永远保留；
- 目标副本已经存在时不得覆盖；
- 目标副本存在人工修改时，以人工修改为准并报告冲突；
- 相同源路径和哈希重复运行时跳过；
- 源文件变化时标记 `source_changed`，不静默更新副本；
- 内容哈希相同的多个源文件只报告重复候选，不自动合并；
- 失败项保留失败证据，可以从失败项继续；
- 用户排除的条目记录为 `excluded`，重复运行默认不重新推荐。

## 6. 用户确认和 Git 边界

- `adopt` 和扫描阶段只读；
- 生成迁移方案属于本地治理记录写入，不执行 Git 受保护动作；
- `apply` 只能处理明确标记为 `approved` 的条目；
- Agent 必须先获得用户对当前迁移方案的明确确认，才能调用应用阶段；
- 迁移可以在代码存在未提交修改时运行，但若目标治理副本路径有未提交修改必须阻止；
- 执行前记录 branch、HEAD 和工作区状态；
- 不自动执行 `git init`、commit、push、PR、merge、tag、release 或删除。

## 7. 项目阶段

新增 `adoption_review` 项目阶段，用于表示已有项目正在接入治理体系。已有 `STATUS.md` 不被重置。迁移完成后，Kit 不根据迁移结果猜测 `active_development` 或 `maintenance`，由用户或 Agent 根据事实更新。

## 8. 非范围

- 业务代码、测试代码或目录结构重构；
- PDF、Word、Excel、图片等复杂格式的内容转换；
- 文档语义总结、自动拆分、自动合并或自动改写；
- 自动删除、移动或覆盖原文件；
- Web 管理后台、托管式协作服务或模型提供商调用；
- 自动 Git 或远程平台操作；
- 独立原文快照目录。

## 9. 验收标准

- AC-01：已有项目可以执行只读扫描，报告治理文件、文档候选、Git 状态和排除项；
- AC-02：补齐模式只创建缺失文件，不覆盖、移动、删除或合并已有内容；
- AC-03：已有 `STATUS.md` 的项目状态保持不变；没有状态文件时使用 `adoption_review`；
- AC-04：迁移方案生成 `MIG-*` 记录，并为每个候选提供来源、目标、置信度和处理状态；
- AC-05：未批准条目不能被 `apply` 写入；批量批准后仍可逐项排除；
- AC-06：Markdown/纯文本可以生成带来源元数据的 `draft` 治理副本；不支持格式只生成映射报告；
- AC-07：重复、源变化、目标冲突、人工修改和迁移失败均能被确定性报告；
- AC-08：迁移完成后更新 MIG、索引、活动和验证记录；
- AC-09：扫描和迁移不会复制已识别的密钥、密码、证书或敏感配置；
- AC-10：核心 CLI 不执行 Git 受保护动作，且 Agent 无批准时无法应用迁移；
- AC-11：重复运行得到幂等结果，已处理项不会重复生成；
- AC-12：测试覆盖空文档区、已有治理文件、脏工作区、冲突、重复、源变化、不支持格式、敏感文件和失败继续。

## 10. 已确认决策

- v0.2 是迁移功能的首个版本，不回写 v0.1 验收范围；
- 用户选择补齐模式或迁移模式；
- 迁移默认保留原文件并生成治理副本；
- 不保存额外原文快照；
- 新增 `MIG-*` 记录；
- 第一版只自动处理 Markdown 和纯文本；
- 批量批准但保留逐项状态；
- 幂等执行、冲突不覆盖、人工修改优先；
- 新增 `adoption_review`，已有状态不覆盖。
